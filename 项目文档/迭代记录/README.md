# 迭代记录规范

> 目的：**每次迭代都留下可查、可改的痕迹**。出了问题能查到"哪次改的、怎么验证的、影响谁"；换人接手能顺着记录复现。

## 1 什么时候写

| 时机 | 写什么 |
|---|---|
| 开始一个迭代（一个功能分支） | 用 `模板.md` 新建 `YYYY-MM-DD-迭代NN-主题.md`，先填「目标 / 范围」 |
| 每次提交 PR | 在记录里补「变更清单」与「验证记录」 |
| 合并 `main` 并打 tag | 补「遗留问题」「对测试同学的影响」，同时更新 `CHANGELOG.md` |
| 迭代中发现需求/设计问题 | 记到该记录的「待确认」区，并在 PR 描述里引用 Q 编号 |

## 2 命名

```
项目文档/迭代记录/2026-11-12-迭代00-环境基座.md
项目文档/迭代记录/2026-11-20-迭代01-用户模块.md
```

- 日期 = 迭代开始日；编号两位递增；主题用中文短语，避免空格。

## 3 必备内容（模板已含）

1. **关联**：分支名、提交 hash、PR 链接、tag；
2. **依据**：对应需求的 FR/AC 编号或设计文档章节（可追溯性）；
3. **变更清单**：模块 / 文件级改动，不写"优化代码"这种含糊描述；
4. **验证记录**：跑过的命令 + 结果（测试数量、构建产物、接口返回、截图路径）；
5. **遗留问题**：未做的、待确认的，写明谁负责、卡在哪；
6. **回滚方法**：出问题时怎么退回去（回滚提交 / 改回镜像 tag / 恢复数据卷）。

## 4 与其他记录的关系

| 记录 | 读者 | 粒度 |
|---|---|---|
| `CHANGELOG.md` | 使用者、测试同学 | 版本级：有什么、改了啥、怎么用 |
| `项目文档/迭代记录/` | 组内开发 | 迭代级：为什么、怎么做、怎么验证 |
| git commit / PR | 全体 | 提交级：单点改动与评审意见 |
| `项目文档/进度快照.md` | 接手的人 | 当前状态：现在能跑到哪一步 |

四者用 **commit hash / tag / PR 链接** 互相引用，保证 `需求 → 设计 → 代码 → 测试 → 部署` 一条线查得到。

## 5 检查清单（提交 PR 前自查）

- [ ] 迭代记录已更新，含验证命令与结果
- [ ] `CHANGELOG.md` 的 `Unreleased` 已补条目
- [ ] 单元测试随代码提交，`mvn verify` 通过
- [ ] 截图/日志放 `项目文档/截图/` 或记录内引用
- [ ] 涉及部署方式的改动，同步更新 `README.md` 与 `docker/README.md`
