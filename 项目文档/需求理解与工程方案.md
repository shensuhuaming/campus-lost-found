## 1 需求解读结论

### 1.1 系统边界

一个前后端分离的 Web 系统，覆盖「发布 → 检索 → 认领 → 归还」闭环，三个角色：

| 角色 | 能力 | 关键约束 |
|---|---|---|
| 游客 | 浏览已审核通过的列表、详情、留言（只读可见） | 不可发布、留言、认领；所有写操作必须登录 |
| 学生（注册用户） | 注册登录、发布寻物/拾物、编辑/下架自己的信息、留言、认领拾物、接收站内消息 | 只能操作自己的资源；被禁用后不可登录 |
| 管理员 | 审核信息、核验认领、分类管理、用户禁用、数据统计、删除留言 | 管理接口必须做角色校验（NFR-02、AC-05） |

### 1.2 需求 → 模块 → 功能点映射

| 模块 | 功能点（FR） | 后端关注点 | 测试关注点 |
|---|---|---|---|
| 用户 | FR-01 注册、FR-02 登录/退出、FR-03 个人中心、FR-04 账号管理 | BCrypt、JWT 签发/校验、禁用态拦截 | 重复学号拦截、密码错误提示、禁用账号登录失败、越权访问他人资料 |
| 失物信息 | FR-05 发布（≤3 图）、FR-06 编辑/下架、FR-07 上传 | 默认待审核、图片数量与大小校验、仅本人可改 | 边界值（30 字标题、500 字描述、2MB/3 张）、编辑他人物品被拒 |
| 浏览检索 | FR-08 列表分页（12 条）、FR-09 筛选、FR-10 关键词、FR-11 详情 | 只查已审核数据、分页上限、模糊匹配 | 未审核数据不出现、筛选组合、搜索结果正确性 |
| 认领归还 | FR-12 状态流转、FR-13 申请、FR-14 核验、FR-15 关闭 | **状态机是核心**、事务一致性、并发重复申请 | 非法状态跳转、重复申请、通过后其余申请自动拒绝、超时回退 |
| 留言消息 | FR-16 留言、FR-17 站内消息（4 场景、未读数） | 消息落库时机、未读数统计 | 4 个场景各产生一条消息、已读状态、未读数正确 |
| 管理后台 | FR-18 审核、FR-19 分类、FR-20 统计 | 分类被引用不可删、统计口径 | 分类删除约束、统计数据与库一致（AC-07） |

### 1.3 物品状态机（FR-12，实现重点）

数据表里其实是**两个独立字段**，必须分开建模，不能合成一个：

- `audit_status`：0 待审核 / 1 通过 / 2 驳回（审核维度）
- `item_status`：0 进行中 / 1 处理中 / 2 已完成 / 3 已关闭（业务维度）

前端展示的「状态标签」由 `type + audit_status + item_status` 组合推导：

| audit_status | item_status | type=寻物(0) | type=拾物(1) |
|---|---|---|---|
| 0 待审核 | — | 待审核 | 待审核 |
| 2 驳回 | — | 已驳回 | 已驳回 |
| 1 通过 | 0 | 寻物中 | 待认领 |
| 1 通过 | 1 | 已联系到拾到者 | 认领核验中 |
| 1 通过 | 2 | 已找回 | 已归还 |
| 1 通过 | 3 | 已关闭 | 已关闭 |

状态迁移（每条迁移都要有单元测试，见 §6.2）：

| 当前 | 事件 | 目标 | 触发者 | 副作用 |
|---|---|---|---|---|
| 待审核 | 审核通过 | 进行中 | 管理员 | 发「审核通过」消息 |
| 待审核 | 驳回 | 已驳回 | 管理员 | 写 `reject_reason`；发「驳回」消息 |
| 进行中 | 有人认领 / 已联系 | 处理中 | 学生 | 拾物：生成认领申请；寻物：发布者自标记 |
| 处理中 | 核验通过 | 已完成 | 管理员 | 该物品其余申请自动置「拒绝」+ 通知 |
| 处理中 | 核验不通过 | 进行中 | 管理员 | 写 `reply`；通知申请人 |
| 处理中 | 超时 / 放弃 | 进行中 | 定时任务或管理员 | 申请置「拒绝」并释放物品 |
| 进行中 | 发布者或管理员关闭 | 已关闭 | 学生/管理员 | 管理员需填理由 |
| 已完成 | 关闭 | 已关闭 | 发布者/管理员 | 建议禁止，或单独归档（待设计确认） |
| 已驳回 | — | 终态 | — | 是否允许重新提交？**规格未定义** |

**规格里已发现的规则缺口**：FR-14 把「通过认领」直接写成 `item_status = 已归还`，而 5.2 的 `item_status` 枚举里 2 表示「已完成」。二者应统一为：**通过 → `item_status = 2`**，展示文案再按 `type` 区分「已归还 / 已找回」。实现时以枚举为准，避免出现两个含义重叠的状态。

## 2 数据模型（按 5.2 数据字典的初稿 + 我的补全建议）

V1.0 只给了主要字段，实际建表还需补：主键策略、时间戳、逻辑删除、外键与索引、字符集（`utf8mb4`）。以下带 *待确认* 的项需要设计组在 DDL 中定案。

| 表 | 规格已给字段 | 建议补充（待确认） |
|---|---|---|
| `user` | id、student_no、password、nickname、phone、role、status、created_at | `updated_at`；`student_no` 唯一索引；role/status 默认值 |
| `category` | id、name、sort、created_at | name 唯一；初始 6 条种子数据 |
| `lost_item` | id、type、title、description、category_id、user_id、happen_time、happen_place、contact、audit_status、reject_reason、item_status、created_at、updated_at | 审核时间/审核人；关闭理由（复用 `reject_reason` 还是新增 `close_reason`）；`type+item_status+category_id+created_at` 组合索引 |
| `item_image` | id、item_id、url、sort | 存储方式：本地 `/uploads` 挂载卷 还是 MinIO（见 §7） |
| `claim` | id、item_id、applicant_id、detail_desc、status、reply、admin_id、created_at | 唯一约束 `(item_id, applicant_id)`；`updated_at` |
| `comment` | id、item_id、user_id、content、created_at | 删除标记（物理/逻辑删除） |
| `message` | id、to_user_id、from_user_id、type、content、item_id、is_read、created_at | `type` 的取值域（见 §8 Q4）；`to_user_id+is_read` 索引 |

关键一致性规则（必须由 Service 层 + 事务 + 唯一索引共同保证）：

1. 同一用户对同一物品只能有一条认领申请（DB 唯一索引兜底，Service 先行校验）；
2. 物品进入「已完成」时，同一物品其余「待核验」申请批量置「拒绝」，并逐一通知；
3. 分类下存在物品时禁止删除（FR-19）；
4. 审核通过前，物品不得出现在任何前台列表/检索结果中（FR-05、FR-08）。

## 5 单元测试与接口测试策略（我的交付职责）

**分层**：单元测试（不依赖 Spring 容器、不连库）为主，接口测试（MockMvc / REST Assured）为辅；系统级功能测试由测试同学用 Docker 环境执行。

| 技术 | 用途 | 注意 |
|---|---|---|
| JUnit 5 + Mockito | Service 层逻辑、状态机、边界值 | Service 测试全部 mock Mapper |
| MockMvc（`@WebMvcTest`） | Controller 路由、参数校验、权限注解 | 需要设计确认统一错误码 |
| Testcontainers（MySQL） | 仓储层/集成测试 | 依赖 Docker，CI 与本地一致；可选 |
| Vitest（若前端也要覆盖） | 组件与工具函数 | 建议放独立任务，不阻塞后端 |

**核心用例清单（编码即写，随 PR 提交）**：

- 注册：学号重复 → 拒绝；两次密码不一致 → 拒绝；密码落库为 BCrypt；密码长度 6~20 边界；
- 登录：账号不存在/密码错/禁用 → 统一提示；成功返回 JWT；
- 发布：标题 30/31 字、描述 500/501 字、图片第 4 张被拒、2MB 边界、jpg/png 以外类型被拒；
- 状态机：上表每条迁移一条用例 + 非法迁移（如 待审核 → 已完成）必须抛业务异常；
- 认领：重复申请被拒；通过后其余申请自动拒绝（断言事务内批量更新与消息条数）；
- 权限：学生访问 `/admin/**` 返回 403；学生编辑他人物品返回 403；
- 检索：未审核数据不命中；分页大小上限生效；关键词命中标题或描述；
- 分类：删除有物品的分类被拒；
- 消息：审核通过/驳回/收到认领/认领结果 4 个场景各产生消息，未读计数正确。

覆盖率目标：Service 层行覆盖 ≥70%、状态机与认领核验分支 **100%** 覆盖（以 JaCoCo 报告为准）。

### 7.1 落地时踩到的坑（已定位，已在仓库中处理）

| 问题 | 现象 | 原因 / 解法 |

| Maven 本地仓库不可写 | `mvn` 报 `AccessDeniedException: ...\apache-maven-3.9.12\mvn_repo\...` | `Maven安装目录\conf\settings.xml` 把 `localRepository` 指到了只读目录。本机构建加 `-Dmaven.repo.local=%USERPROFILE%\.m2\repository`；IDEA 把 Local repository 改到 `C:\Users\<你>\.m2\repository`；**容器内构建**已改用 `backend/maven-settings.xml`（阿里云镜像，不受本机配置影响） |

| Docker Desktop 不随开机启动 | 重启后 `docker` 报 `pipe ... cannot find the file` | 手动启动 Docker Desktop，等引擎就绪（约 15 秒） |

## 8 需要设计组 / 需求方确认的问题（阻塞编码）

> 这些是 V1.0 里没有定义、但直接影响表结构和接口的点。建议在设计文档里逐条给出结论，我按结论实现。

- **Q1 字段语义冲突**：FR-14「认领通过 → 已归还」与 5.2 `item_status=2 已完成` 是否统一为「已完成」？（我的建议：统一为 2，文案按 type 区分）
- **Q2 认领失败后的回退**：「不通过 → 退回进行中」由谁触发？超时是多少小时（定时任务还是管理员手动）？同物品其他待核验申请在「通过」之外（如关闭、超时）时如何处理？
- **Q3 寻物信息的「处理中」如何产生**：规格写「有人认领/已联系」，寻物没有认领表记录，是否由发布者在「我的发布」里手动点「已联系」？谁有权限改？
- **Q4 站内消息 `type` 取值域**：审核通过/驳回/留言/收到申请/申请结果，5 类是否就固定这 5 个枚举值？`from_user_id=0` 表示系统，留言提醒是否用真实发布者 id？
- **Q5 联系方式展示**：`contact` 在详情页对游客是否可见？涉及隐私时是否登录后才显示？
- **Q6 鉴权细节**：JWT 有效期、是否做刷新、密码错误次数限制、退出是否要服务端黑名单？
- **Q7 分页与搜索排序**：FR-10「按相关度与时间排序」——MySQL 无原生相关度，是否接受「命中次数/标题优先 + 时间倒序」的简化实现？
- **Q8 图片存储**：本地磁盘卷 or MinIO？URL 是相对路径还是完整地址？nginx 是否托管 `/uploads`？
