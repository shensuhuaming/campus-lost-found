## 1 开发任务

**目标**：给管理员一套把住入口、管好数据、看清趋势的工具，使"发布→审核→展示"与"认领→核验"两条主链路可控。

**范围**

- 是：待审核列表 + 通过/驳回（通知发布者）、分类增删改（引用保护）、用户列表与启用/禁用、统计四项指标 + 分类分布 + 近 30 天趋势。
- 不是：内容批量操作、操作审计日志、导出报表、图表下钻。

**依赖**：`lost_item`、`category`、`user`、`claim`；`MessageService`（审核结果）；ECharts（前端）。

**完成标准**

1. 待审队列只含"待审核且未关闭"；重复审核 2003；驳回必填理由；
2. 审核通过后前台立即可见，驳回后发布者收到含理由的消息；
3. 分类重名 5001、被引用删除 5002（提示条数）、不存在 5003；
4. 用户列表带发布数/认领数；不能操作自己与其他管理员；禁用即时生效；
5. 统计口径与《API 规格》7.9 一致，趋势缺日补零。

## 2 设计要点

### 2.1 审核

- 条件更新：`UPDATE lost_item SET audit_status=?, reject_reason=? WHERE id=? AND audit_status=0`，影响行数 ≠1 → 2003（并发/重复审核）；
- 通过时清空 `reject_reason`；驳回时写入 1~100 字原因（无理由 1001）；
- 通知发布者（`type=1`）。

### 2.2 分类

- 名称唯一（新增与改名都查重，排除自身）；
- 删除前统计 `lost_item`（**含已关闭**），有引用则 5002 并返回条数；
- 排序值越小越靠前。

### 2.3 用户

- 列表批量统计发布数与认领数（两条 `GROUP BY`，避免 N+1）；
- 禁用校验：不能禁用自己、不能禁用其他管理员（2002）；
- 禁用后拦截器即时拦截（登录 1004）。

### 2.4 统计口径（已批准偏差）

| 指标 | 口径 | 说明 |
|---|---|---|
| `totalItems` | 全表条数（含待审核、已关闭） | 与 API 7.9 一致；不随筛选变化 |
| `pendingAudit` | `audit_status=0 AND item_status<>3` | 排除已关闭 |
| `completedClaims` | `claim.status=1` 的条数 | 成功归还次数 |
| `returnRate` | 已完成拾物 ÷ 已过审拾物 ×100（1 位小数） | 分母为已过审拾物（含已关闭） |
| `categoryStats` | 各分类信息数、已完成数、该分类归还率 | 一次 `LEFT JOIN` 聚合 |
| `trend` | 近 N 天每日发布量（默认 30，范围 7~30），缺日补 0 | `DATE(created_at)` 分组 + 应用层填充 |

> 偏差说明：M6 迭代前曾按"全部信息"计算归还率分母，评审后统一为"已过审拾物"，已登记在迭代 07/10 记录中。

## 7 遗留与风险

| 项 | 说明 | 影响 | 计划 |
|---|---|---|---|
| 审核结果不可撤销 | 通过后如需下架只能"关闭"（终态） | 中 | 建议二期加"撤回审核" |
| 统计无缓存 | 每次请求 6 条聚合 SQL | 低（数据量小） | 二期可加缓存 |
| 无操作审计日志 | 谁审的、谁禁的只在 `claim.admin_id` 有 | 中 | 建议加 `admin_log` 表 |
| 分类删除为物理删除 | 与设计一致（有引用保护） | 低 | — |
| 图表未适配移动端 | 后台建议电脑使用 | 低 | 二期 |
