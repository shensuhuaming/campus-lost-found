## 1 开发任务

**目标**：让"东西是我的"变成可核验的申请，并把核验结果正确反映到物品状态与双方通知上。

**范围**

- 是：发起认领、管理员待核验列表（三表关联、关键词）、核验通过（含其余申请自动拒绝）、核验拒绝（可回退物品状态）。
- 不是：认领撤销（设计未要求）、线下交接流程、申诉。

**依赖**：`claim` 表（唯一索引 `uk_claim_item_applicant`）、`lost_item`、`MessageService`、`ItemStatusMachine.checkClaim`。

**完成标准**

1. 认领后物品 0→1，重复申请 3003，认领自己 3001，未过审 2004，已完成/关闭 2003；
2. 核验通过：物品 1→2、本申请通过、其余待核验自动拒绝并各自收到消息，**单事务**；
3. 核验拒绝：必填理由，且仅在无其他待核验申请时物品退回 0；
4. 并发安全：条件更新 + 唯一索引兜底；
5. 单元测试覆盖每个失败分支与消息推送。

## 2 设计要点

### 2.1 认领状态机（`ItemStatusMachine.checkClaim`）

```
待核验(0) ──核验通过──→ 已通过(1)
     └────核验拒绝──→ 已拒绝(2)
```

只有 `status=0` 可操作，否则 3002（`CLAIM_STATUS_ILLEGAL`）。

### 2.2 关键规则

| 规则 | 实现 |
|---|---|
| 发起认领顺序 | 物品存在且已过审 → 非已完成/关闭 → 非本人 → 仅拾物 → 无历史申请；命中即返回对应错误码 |
| 唯一约束兜底 | 捕获 `DuplicateKeyException` 同样返回 3003 |
| 物品 0→1 | 条件更新（`WHERE item_status=0`），影响行数为 0 说明已处理中，不算失败 |
| 核验通过（单事务） | 物品 1→2（影响行数≠1 → 2003 回滚）→ 本申请置 1 → 其余待核验置 2（回复"该物品已被他人认领"）→ 通知申请人/被拒者/发布者 |
| 核验拒绝 | 必填 1~200 字；本申请置 2；统计剩余待核验数，为 0 才把物品 1→0；通知申请人 |
| 消息时机 | 全部走 `afterCommit`，业务回滚不会发通知 |

### 2.3 数据表

`claim(id, item_id, applicant_id, admin_id, detail_desc, status, reply, created_at, updated_at)`；唯一索引 `uk_claim_item_applicant(item_id, applicant_id)`。

> 提示：唯一索引意味着**同一用户对同一物品只能申请一次**，被拒后本人不能重申（其他人可申请）。已在《使用说明书》与交接说明"设计如此"清单中标注。

## 7 遗留与风险

| 项 | 说明 | 影响 | 计划 |
|---|---|---|---|
| 被拒后本人无法重申 | 唯一索引决定；设计未提供撤销/重申请 | 中（体验） | 建议二期加"撤销申请"或允许拒绝后重申请 |
| 无认领撤销 | 设计未要求 | 低 | 二期 |
| 核验无二次确认 | 管理员误点即通过，且不可回滚 | 中 | 建议前端加确认；后端可加"撤销核验"（需设计） |
| 通知只站内 | 无短信/邮件 | 低 | 二期 |
