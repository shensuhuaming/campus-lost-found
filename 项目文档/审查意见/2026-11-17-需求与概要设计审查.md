## 一、必须修改（阻塞编码）

### A1 统一响应码与已实现骨架冲突

| 项 | 现状 |
|---|---|
| 概要设计 §4.2.1 / §7.1 | `code: 200` 表示成功，错误码 400/401/403/404/500 |
| 已实现骨架 | `code: 0` 表示成功，业务错误码分段 1xxxx~9xxxx |
| 冲突 | 前端拦截器、测试用例、异常处理都按 `code === 0` 判断 |

**影响**：不改则所有前端请求判错、所有接口测试用例要重写。

**建议（二选一，需定稿）**：
- **方案 A（推荐，改动小）**：保留 `code: 0` 成功 + 业务错误码分段，把概要设计 §4.2.1/§7.1 改成与代码一致，并补充"HTTP 状态码表达协议层，body.code 表达业务结果"的约定；
- 方案 B：按概要设计的 `200` 改代码，同时明确"业务失败时 HTTP 仍返回 200 还是 4xx"（概要设计没说清，这点本身也是缺口）。

### A2 寻物信息到不了"已完成"

状态转换图里，`处理中 → 已完成` 的唯一触发是**管理员核验通过**；但寻物信息没有认领申请，管理员没有可核验的对象。结果是：**寻物信息一旦进入"处理中（已联系到拾到者）"就永远无法标记"已找回"**，FR-12 的"寻物 = 已找回"、AC-04、FR-20 的归还/统计都闭环不了。

**建议**：状态机按 `type` 分支，写进设计文档：

| 类型 | 进行中 → 处理中 | 处理中 → 已完成 |
|---|---|---|
| 拾物 | 有人提交认领申请（系统自动） | 管理员核验通过 |
| 寻物 | 发布者点"已联系到拾到者"（管理员可代操作） | 发布者点"已找回"（管理员可代操作） |

并补一个接口，避免为每种迁移开一个 URL：

```
PUT /api/items/{id}/status    body: { "targetStatus": 1|2|3, "reason": "可选" }
```

服务端集中校验"角色 + 当前状态 + 目标状态 + 类型"是否合法，非法一律抛业务异常（这正好是单元测试 100% 覆盖的地方）。

### A3 两个状态的耦合没定清楚，会算错标签和统计

现状：`audit_status`（待审核/通过/驳回）与 `item_status`（进行中/处理中/已完成/已关闭）是两个字段，但设计里没说清"未通过审核时 item_status 是什么"。

- 新建记录 `item_status` 默认 0 = **进行中**，于是"待审核"和"已驳回"的物品在数据库里也是"进行中"；
- 状态转换图新增了 `待审核 --发布者撤回--> 已关闭`，但撤回后 `audit_status` 仍是 0（待审核），**后台待审核列表会一直出现这条已关闭的信息**；
- FR-20 统计"物品总量（分状态）"会把这些都算进去。

**建议**：
1. 明确 `item_status` 仅在 `audit_status=1` 时有业务含义，前端标签与统计一律先过审核状态；
2. 撤回要么**禁止**（需求 FR 里本来没定义撤回，删掉这条边最省事），要么新增 `audit_status=3 已撤回`，后台待审列表按 `audit_status=0 AND item_status<>3` 过滤；
3. 统计口径写死：物品总量 = `audit_status=1` 的总数；归还率 = 拾物中 `item_status=2` 数 ÷ 拾物中 `audit_status=1` 数。

### A4 关闭/下架理由没有字段

FR-06 要求"管理员下架任何违规信息**并填写理由**"，FR-15 关闭信息、A3 里的撤回也可能需要理由；但 `lost_item` 只有 `reject_reason`（驳回理由，属审核维度）。

**建议**：新增 `close_reason VARCHAR(200)`，与 `reject_reason` 语义分开。否则只能把下架理由塞进 `reject_reason`，后续统计"驳回率"会被污染。

### A5 前台拿不到分类列表

接口清单里分类相关接口全部在 `/api/admin/categories` 且要求管理员鉴权；而首页的"分类筛选"（FR-09）是游客也要用的。

**建议**：补公开接口 `GET /api/categories`（返回 id、name、sort，按 sort 升序），管理接口保持不变。

### A6 图片访问路径没定，Docker 部署下必然 404

概要设计 §9.3 只写了"图片采用本地静态存储"，§10 又把它列为"待明确"。当前部署形态是 nginx（前端容器）→ backend（后端容器），**后端容器的本地目录 nginx 访问不到**，`/uploads/xxx.jpg` 会 404。

**建议**：三选一并在设计里写死：
1. nginx 增加 `location /uploads/ { proxy_pass http://backend:8080; }`，后端只读；图片存后端卷 `uploads`（**改动最小，推荐**）；
2. 后端提供 `GET /api/files/{name}` 读卷输出（走已存在的 `/api` 代理，最稳）；
3. 引入 MinIO/对象存储（课程项目没必要）。
