## 一、必须修改（阻塞编码 / 会产生错误数据）

### D1 关闭理由（closeReason）接收了但无处存

| 项 | 内容 |
|---|---|
| 位置 | 说明书 4.2.4「输入：id 与可选的 closeReason」；API 3.3 关闭信息 |
| 事实 | `lost_found.sql` 的 `lost_item` 没有 `close_reason` 列，伪代码 `close(Long id)` 也没有接收该参数 |
| 后果 | FR-06 要求「管理员下架违规信息**并填写理由**」，理由被直接丢弃；AC 无法验证 |
| 建议 | 新增 `close_reason VARCHAR(200)`，伪代码改为 `close(Long id, String reason)` 并写入；`reject_reason` 继续只用于审核驳回 |

### D2 待审核信息可以被"关闭"，审核状态却还是待审核

| 项 | 内容 |
|---|---|
| 位置 | 4.4.1 迁移表允许 `0/1 → 3`；U2.4 关闭；4.6.1 审核列表默认 `auditStatus=0` |
| 事实 | 待审核信息的 `item_status` 默认就是 0，所以**待审核 = 可以关闭**；关闭只改 `item_status=3`，`audit_status` 仍为 0 |
| 后果 | ① 后台待审列表会一直出现这条已关闭信息；② 管理员若误点"通过"，会得到"审核通过 + 已关闭"的矛盾数据；③ 统计里"待审核数"虚高 |
| 建议 | 二选一并写进设计：<br>① 关闭待审核信息时同时把 `audit_status` 置 2（驳回）并写 `close_reason`；<br>② 待审核列表条件改为 `audit_status=0 AND item_status<>3`，并禁止对 `item_status=3` 的记录审核 |

### D3 编辑会把已通过的信息打回待审核，但在途认领不处理

| 项 | 内容 |
|---|---|
| 位置 | 4.2.3 U2.3 编辑：只校验 `item_status != 2`，随后 `audit_status=0` |
| 事实 | 一条"处理中"（有 1 条待核验认领）的信息被发布者编辑后，回到待审核，**认领申请仍是待核验** |
| 后果 | 管理员核验通过 → 把一条"未审核"的信息置为"已完成"；前台不可见（`audit_status≠1`），但认领流程已闭环，数据自相矛盾 |
| 建议 | 编辑前置条件收紧为「`item_status=0` 且不存在待核验申请」；或在编辑时把该信息下所有待核验认领置"拒绝"并通知，二者择一写入设计 |

### D4 统计口径与需求不一致（近 7 日 vs 近 30 天；总数含未审核）

| 项 | 内容 |
|---|---|
| 位置 | 4.6.4 U6.4、5.5 SQL #5、API 7.9 |
| 事实 | 需求 FR-20 明确「**近 30 天**新增趋势折线图」，设计与接口都写"近 7 日"；另"失物信息总数 = 全部记录（含各审核状态）"，而"归还率"只算已审核通过的拾物，"分类分布"又没有审核过滤 |
| 后果 | AC-07「统计图表数据与数据库实际数据一致」按需求验收会不通过；三项指标口径混用，前端无法解释"总数 100 但分类占比只覆盖 60"的现象 |
| 建议 | ① 趋势改为近 30 天（与 FR-20 对齐）；② 在表 4-10 增加一列"统计范围"，逐项写明是否含待审核/驳回/关闭；③ 分类分布 SQL 增加 `audit_status=1`，与归还率口径一致，或明确标注"含全部状态" |

### D5 消息用 REQUIRES_NEW 会产生"幽灵通知"

| 项 | 内容 |
|---|---|
| 位置 | 5.4 事务边界、U5.3、4.4.3 时序说明 |
| 事实 | 设计明确"消息写入用独立事务，不受外层回滚影响"，理由是"通知优先送达" |
| 后果 | 核验通过时若物品条件更新失败整体回滚，申请人**仍会收到"你的认领申请已通过"**，但库中申请仍是待核验 → 用户拿着错误信息来找管理员，属于典型的分布式一致性问题在小系统里的复现 |
| 建议 | 改为与外层同事务（回滚则无通知，最安全）；若确实要"优先送达"，用 `TransactionSynchronization.afterCommit` 在提交成功后推送。不建议保留现在的写法 |

### D6 图片 URL 只校验数量，不校验来源与归属

| 项 | 内容 |
|---|---|
| 位置 | U2.1 输入 `images` 为"图片 URL 数组"，仅校验 `size<=3`；U2.2 上传接口对任何登录用户开放 |
| 事实 | 服务端不校验 URL 是否是本系统上传的文件、是否是本人上传、路径是否合法 |
| 后果 | 用户可把任意外部 URL 或他人图片地址挂到自己发布的信息上（内容安全 + 越权引用）；若后续拼接路径时不加白名单，还存在路径穿越风险 |
| 建议 | 上传接口返回一个由服务端登记的标识（如 `upload_token` 或写 `temp_upload` 表），发布/编辑时校验"存在、未使用、属于当前用户、前缀为 `/uploads/`"；至少做前缀 + 存在性校验 |

### D7 缺少 ItemImageMapper，类图与伪代码矛盾

| 项 | 内容 |
|---|---|
| 位置 | §3.2 写"6 个 Mapper"、图 3-4 列出 6 个 Mapper；U2.1/U2.3 伪代码使用 `itemImageMapper` |
| 后果 | 按文档实现会缺一个 Mapper，或者图片表操作被塞进 ItemMapper 但没有设计说明 |
| 建议 | 明确为 7 个 Mapper（补 ItemImageMapper），或写明"图片表操作由 ItemMapper 的 `insertImages/replaceImages` 承担" |

## 五、对我方已实现骨架的影响

| 现状 | 按详细设计需要变成 | 工作量 |
|---|---|---|
| `ApiResponse.code=0` 成功 | `code=200` 成功；业务码 1xxx~9999；HTTP 状态按错误类型 | 小（改 1 个类 + 拦截器 + 2 个测试） |
| 数据库名 `campus_lost_found` | `lost_found`；排序规则 `utf8mb4_general_ci` | 小（改 init 脚本 + compose 环境变量 + 重建卷） |
| `db/init` 的 7 张表（无外键） | 用设计方 `lost_found.sql`（含外键、索引、唯一约束） | 小（直接替换并保留可重复执行） |
| 时间格式 `OffsetDateTime` ISO-8601 | `LocalDateTime` + `yyyy-MM-dd HH:mm:ss` | 小 |
| 无 `/uploads` 反代 | nginx 加 `location /uploads/` 指向 backend | 小（部署侧） |
| 无 JWT / MyBatis-Plus | 按 2.3 包结构引入 | 中（第一个业务迭代） |

> 结论：**骨架不需要重构**，只需 4 处小改 + 引入 MyBatis-Plus，即可与详细设计对齐。
