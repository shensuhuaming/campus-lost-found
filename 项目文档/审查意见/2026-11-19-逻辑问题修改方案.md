## 二、逐条方案

### P0-1 寻物信息的状态推进

**现有文档**：4.4.1 迁移表里 `0→1` 只由"有人提交认领申请"触发（U4.2 只允许拾物）；`1→2` 只由"核验通过"触发（U4.3 只处理认领）。
**问题**：寻物信息没有认领对象，永远停在 0 或只能被关闭。

**方案（改动最小的加法）**：保留现有认领链路不动，只给寻物补一条自己的推进路径。

| 对象 | 当前 | 事件 | 目标 | 触发者 |
|---|---|---|---|---|
| 物品 | 0 进行中 | 标记"已联系到拾到者"（仅 type=0） | 1 处理中 | 发布者（管理员可代操作） |
| 物品 | 1 处理中 | 标记"已找回"（仅 type=0） | 2 已完成 | 发布者（管理员可代操作） |

- 新增程序单元 **U2.5 寻物状态推进**，接口 `PUT /api/items/{id}/status`，body `{"targetStatus": 1|2}`；
- 校验顺序：信息存在(2004) → 本人或管理员(2002) → `type=0` 且 `audit_status=1`(2003) → 状态机允许(2003) → 条件更新（`WHERE item_status=原值`，影响行数≠1 抛 2003）；
- 副作用：更新后推送系统消息给发布者自己确认（可选，建议做，保持与其他状态变更一致）；
- 拾物仍走原认领链路，`targetStatus` 对 type=1 一律 2003；
- 前端：详情页与"我的发布"对 `type=0 && item_status∈{0,1}` 显示对应按钮；
- 单测：4 条（寻物 0→1 成功、1→2 成功、拾物调用 2003、跳级 0→2 2003）。

**文档改动**：4.4.1 迁移表加 2 行、3.4 程序单元清单加 U2.5、4.2 模块加 4.2.5 小节、API 规格 3.5 节、图 4-1~4-9 不新增图。

### P0-2 关闭理由落库

**现有文档**：4.2.4 输入含 `closeReason`；SQL 无对应列。
**方案**：
- `lost_item` 在 `reject_reason` 之后加一列：
  ```sql
  `close_reason` VARCHAR(200) NULL COMMENT '关闭/下架理由；管理员下架必填',
  ```
- `close(Long id, String reason)`：
  - 管理员关闭：`reason` 必填（1~100 字，否则 1001），写入 `close_reason`；
  - 发布者关闭：`reason` 可选，写入 `close_reason`；
- 详情/后台列表 VO 返回 `closeReason`（后台用于核查）；
- `reject_reason` 保持只用于审核驳回，语义不混。

**文档改动**：SQL 加列、5.3.3 表加一行、4.2.4 伪代码与参数、API 3.3 请求体、5.5 SQL 备注。

### P0-3 待审核信息被关闭后的审核态

**现有文档**：U2.4 允许 `0→3`（待审核的 `item_status` 也是 0）；4.6.1 待审列表默认 `audit_status=0`。
**方案（不改 DDL、不新增枚举）**：
- 明确规则：**关闭不改变 `audit_status`**，但"已关闭"的信息不再进入待审队列、不可再审核；
- 4.6.1 审核列表 SQL 增加 `AND item_status <> 3`；
- `audit()` 入口增加校验：`item_status == 3` → 2003；
- 统计"待审核数"同样加 `item_status <> 3`；
- 文档补一句：待审核信息可被发布者关闭，关闭后审核状态保持"待审核"但视为已撤下，不再出现在待审列表。

**为什么不选"关闭即置 audit_status=2"**：`audit_status=2` 在文档里语义是"驳回"，会与 `reject_reason` 冲突，改动面更大。

### P0-4 编辑与在途认领

**现有文档**：U2.3 只禁止 `item_status=2`，编辑后 `audit_status=0`。
**方案**：前置条件改为 **`item_status = 0` 才可编辑**（表 4-6 第 2 行同步改），其余一律 2003。
- 理由：`item_status=1` 意味着已有人认领在等核验，此时改描述会误导管理员；
- 实现只改一个判断，不加字段、不加流程；
- 前端：`item_status≠0` 时隐藏"编辑"按钮并给出提示。

### P0-5 图片 URL 校验

**现有文档**：`images` 只校验数量 ≤3。
**方案（不新增表）**，在 U2.1/U2.3 保存前逐条校验：
1. 正则白名单：`^/uploads/\d{6}/[0-9a-f]{32}\.(jpg|jpeg|png)$`（同时挡住外部链接与 `../` 路径穿越）；
2. 文件存在：`Files.exists(user.dir + url)`；
3. 未被引用：`SELECT COUNT(*) FROM item_image WHERE url=?` 必须为 0（编辑时排除本条信息自己的图片）；
4. 数量 ≤3（已有）。
- 残余风险：无法阻止"引用他人刚上传、尚未使用的图片"，课程演示可接受，在文档中写明该限制。

### P0-6 消息推送事务

**现有文档**：U5.3 用 `REQUIRES_NEW`，自述"通知优先送达"；9.5 又写"推送失败不影响主业务"。
**方案**：
- 去掉 `REQUIRES_NEW`；
- `MessageService.push()` 内判断：有事务则 `TransactionSynchronizationManager.registerSynchronization(...afterCommit → 落库)`；无事务直接落库；
- 推送异常仍捕获记日志（与 9.5 一致），不回滚主业务；
- 文档把取舍说明改为"**提交后通知**：业务成功才通知，避免回滚后误报；通知失败只记日志不影响业务"。

### P0-7 统计口径

**现有文档**：FR-20 要近 30 天；U6.4 写近 7 日；"总数"含全部状态，"归还率"只算已通过拾物，"分类分布"无过滤。
**方案（口径统一为"已对外发布"）**：
| 指标 | 新口径 |
|---|---|
| 失物信息总数 | `audit_status=1`（已通过） |
| 待审核数 | `audit_status=0 AND item_status<>3`（与 P0-3 一致） |
| 已完成数 | `item_status=2`（已完成必是已通过，天然一致） |
| 归还率 | 不变（拾物 `audit_status=1` 中 `item_status=2` 占比） |
| 趋势 | **近 30 天**，`audit_status=1`，按日补 0 |
| 分类分布 | `audit_status=1`，占比合计 100% |
- SQL #5 的日期范围改 30 天；#6 的过滤条件移到 `ON` 上（保留没有信息的分类，计数 0）。

### P0-8 公开分类接口

**现有文档**：API 7.3 的括号里提了一句"可公开调用"，无正式条目。
**方案**：API 规格新增 **4.3 分类列表（公开）**：
```
GET /api/categories   权限：公开
响应 data: [{ "id": 1, "name": "证件", "sort": 1 }, ...]  按 sort 升序
```
管理端 `GET /api/admin/categories`（含 itemCount）保持不变。
