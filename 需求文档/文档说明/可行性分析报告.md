## 1 引言

### 1.1 编写目的

在投入开发前，从技术、经济、操作、法律与社会四个方面论证本项目的可行性，作为立项依据，供指导教师与项目组评审参考。

### 1.2 项目背景

校园内物品遗失与拾取事件频繁，现有公告栏、群聊等方式存在信息分散、检索困难、认领缺乏核验等问题。本项目拟开发基于 Web 的校园失物招领系统，实现信息发布、检索、认领归还全流程线上管理（详见《需求规格说明书》1.2）。

### 1.3 分析范围

本机运行的 Web 系统，覆盖用户、失物信息、浏览检索、认领归还、留言消息、管理后台六大模块。

## 2 技术可行性

### 2.1 技术路线

| 层次 | 技术选型 | 说明 |
|---|---|---|
| 后端 | Spring Boot 3.x + MyBatis-Plus + MySQL 8 | 老师指定，主流企业级组合 |
| 前端 | Vue 3 + Element Plus + ECharts | 组件化开发，界面与图表成熟 |
| 鉴权 | JWT + BCrypt 密码加密 | 无状态认证，安全成熟 |

### 2.2 技术成熟度分析

以上技术均为业界广泛使用的开源技术，社区活跃、文档与教程丰富、版本稳定，遇到问题可快速检索解决，技术风险低。

### 2.3 团队技能分析

项目组成员均已修读程序设计、数据库、Web 开发等相关课程，具备 Java、SQL、前端基础开发能力；开发工具（IDEA、VS Code、MySQL Workbench）为校园常用工具，无额外学习门槛。

### 2.4 主要技术风险与对策

| 风险 | 影响 | 对策 | 风险等级 |
|---|---|---|---|
| 前后端接口约定不一致 | 联调返工 | 编码前先定接口文档（详细设计阶段产出） | 低 |
| 图片上传与存储配置问题 | 演示异常 | 图片存本机目录、限制 3 张/2MB，简化配置 | 低 |
| JDK/Node 版本不一致 | 运行报错 | 组内统一 JDK 17、Node.js 18+ 版本 | 低 |

**结论：技术可行。**

## 3 经济可行性

### 3.1 开发成本

| 成本项 | 说明 |
|---|---|
| 软件成本 | 技术栈全部开源免费（Spring Boot、Vue、MySQL 社区版），无软件采购费用 |
| 硬件成本 | 本机部署演示，无需购买服务器、域名 |
| 人力成本 | 开发人力为课程设计学时，无额外资金投入 |

### 3.2 效益分析

1. 完成课程设计任务，达成教学要求；
2. 解决校园失物信息分散、冒领风险等实际痛点，具备真实使用价值；
3. 提升团队需求分析、设计、编码、测试的完整工程实践能力。

**结论：经济可行。**

## 4 操作可行性

### 4.1 用户操作

目标用户为在校学生，普遍熟悉网页操作。系统采用"学号+密码"登录，界面基于 Element Plus 简洁组件设计，核心操作（发布、搜索、认领）路径不超过 3 次点击，无学习成本。

### 4.2 管理操作

管理员所有操作（审核、核验、分类管理、统计）均在可视化后台界面完成，无需命令行操作，培训成本低。

### 4.3 运行维护

本机演示模式：启动后端（一条启动命令）+ 前端（一条启动命令）+ 本地 MySQL 即可运行，维护简单。

**结论：操作可行。**

## 5 法律与社会可行性

1. **个人信息保护**：仅收集学号、昵称、联系方式等必要信息，密码加密存储，不收集身份证号等敏感信息；
2. **信息内容管理**：发布内容仅限物品信息，管理员审核过滤违规内容，可下架不当信息；
3. **防冒领机制**：认领须经管理员核验物品细节，界面提示冒领他人财物的法律后果；
4. **知识产权**：技术栈均为开源许可，无侵权风险。

**结论：法律与社会可行。**

## 6 结论

本项目在技术、经济、操作、法律与社会四个方面均可行，需求明确、风险可控，建议立项进入概要设计阶段。

## 7 可行性实测记录（环境基座 v0.1.0，2026-11-12）

> 本章由编码与单元测试组补充：把第 2~5 章的定性判断落到可验证的实测数据上。所有结论均可在 `项目文档/迭代记录/2026-11-12-迭代00-环境基座.md` 中复现。

### 7.1 技术路线实测

| 验证项 | 实测结果 | 说明 |
|---|---|---|
| JDK 17 + Spring Boot 3.5.9 | ✅ 编译、单测、打包通过 | 生成 27.5 MB 可执行 jar，`java -jar` 直接启动 |
| Vue 3 + Element Plus + Vite 6 | ✅ 类型检查与生产构建通过 | 产物 gzip 后约 375 KB JS + 49 KB CSS |
| MySQL 8.0 | ✅ 建表与种子数据一次通过 | 7 张表、6 个分类，`utf8mb4`、时区 +08:00 |
| 后端连库 | ✅ 自检接口返回 `database.status=UP` | 本机进程与容器内均验证 |
| Docker 全栈 | ✅ 3 容器启动、健康检查通过 | mysql / backend / frontend，nginx 反代 `/api` 正常 |
| 单元测试与覆盖率 | ✅ JUnit 5 + MockMvc + JaCoCo 可用 | `mvn verify` 出覆盖率报表 |
| CI | ✅ GitHub Actions 4 次运行全绿 | 后端 verify + 前端构建 |

**结论：技术路线无实质障碍，第 2 章"技术可行"的判断成立。**

### 7.2 成本与工期的实测修正

| 项 | 立项预估 | 实测 | 对计划的影响 |
|---|---|---|---|
| 环境搭建 | 1 人日 | 约 0.5 人日（含镜像拉取等待） | 可提前进入编码 |
| 首次镜像准备 | 未评估 | 5 个基础镜像约 1.8 GB，Docker Hub 直连超时，需走镜像加速器 | 部署文档已写明替代方案，测试同学按文档可自行完成 |
| 后端依赖下载 | 未评估 | 首次约 5 分钟，后续增量构建 <1 分钟 | 建议组内共享 `~/.m2` 缓存 |
| 前端依赖安装 | 未评估 | 首次约 11 分钟 | 已提供 `node_modules` 安装说明 |

### 7.3 已识别的技术风险（立项文档未覆盖）

| 风险 | 实际表现 | 已采取的对策 | 等级 |
|---|---|---|---|
| 工程目录含中文 | Maven 本地仓库不可写、`docker compose` 项目名为空、JaCoCo 写不出数据 | 显式指定本地仓库路径、compose `name: clf`、覆盖率数据文件移到系统临时目录 | 中（已解决） |
| Windows 下 Docker 命名管道权限 | 默认沙箱内 `docker` 命令无法连接引擎 | 由用户在受控终端内执行，或授予完整访问 | 低 |
| Docker Hub 直连不可用 | 拉镜像超时 | 镜像站拉取后 `docker tag` 回官方名，README 已记录 | 中（有替代方案） |
| 本机端口冲突 | 3306 已被本机 MySQL 占用 | 容器映射到 3307 | 低 |
| 全局 `git http.sslverify=false` | 存在中间人风险 | 已在文档中标注，建议推送前关闭 | 低 |

### 7.4 操作与维护可行性实测

- **一键部署可行**：`docker compose --profile full up -d --build` 后访问 `http://localhost` 即可看到自检页面，无需手工建库、导表、改配置；
- **环境自检可观测**：页面直接显示"后端 UP / 数据库 UP"，测试同学不需要看日志判断环境是否就绪；
- **失败可回滚**：`docker compose --profile full down -v` 可完全重置，重建耗时约 1~2 分钟（镜像已就绪时）。

**结论：第 4 章"操作可行"的判断成立，且比立项时的估计更容易交付给测试。**

### 7.5 对后续迭代的可行性提示

1. 概要设计选定的 MyBatis-Plus 与已引入的 `spring-boot-starter-jdbc` 兼容，无需更换基础设施；

3. 单元测试与 CI 基座已就绪，业务模块可以做到"代码 + 用例"同 PR 提交；
4. 设计与需求的 6 个阻塞问题（见 `项目文档/审查意见/2026-11-17-需求与概要设计审查.md`）若不先定，会在第一个业务迭代产生返工，建议作为可行性复核的遗留项跟踪。
